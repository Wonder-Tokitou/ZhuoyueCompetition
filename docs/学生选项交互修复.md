## 复现与原因

旧页面点击策略直接触发 POST，然后把全部按钮禁用；没有单独的选中状态，成功后自动出现下一题。慢网络下三项统一变灰，用户无法确认点中了哪项，连续点击还可能落在新回合上。

学生选项本来就按会话打乱排序，屏幕 A/B/C 是展示序号，不一定等于教师内部 key。旧页面的结果只有摘要和指标，没有策略回执，教师记录只显示内部 key，进一步造成“选错”的观感。

只读核对最近 9 条相关真实记录：已保存结果均对应所提交 key 的冻结快照。该证据排除了这些记录中“后端用 key 取错财务结果”，不能反推出用户每次触摸的实际意图。

前端回归测试在旧实现上明确失败：选 A 后没有任何单独的选中项。后端新增凭据测试在修复前也失败（缺少展示编号/策略文字）。修复后均通过。

## 修复后的不变量

1. 选择只改变本地选中项，不发决策请求；三个策略中最多一项高亮，确认前可修改。
2. “确认提交本回合”才发请求；发送的是选项稳定 key，绝不是展示 index 或字母。
3. 提交期间锁定操作，但保留已选项颜色、文字和保存提示；不能用统一灰色代替选中状态。
4. 保存后回显服务器实际保存的策略和结果；必须点击“继续下一回合”才显示新选项。
5. 同步请求锁阻止确认连击；节点身份防止旧回调再次提交；切换案例后的异步响应不能污染新案例。
6. 请求失败先 GET 核对保存情况；POST 响应丢失不等于未保存。无法核对时只允许“核对已保存进度”，不会盲目重复提交。
7. 教师、学生记录都由冻结快照还原 `display_option` 和 `chosen_label`，`chosen_option` 仍是原始 key。旧记录没有快照时返回空值，不能拿现行案例猜测旧策略。
8. 保留原来的哈希打乱算法，历史会话编号顺序不变化；保留后端顺序校验，重复提交同一回合返回 409，不追加决策。

## 发布和防复发

前端已构建到 `frontend/dist`。运行中的服务读取新构建文件，新开/刷新页面即可加载选择确认流程。已经打开的旧页面要刷新。

后端进程需重启才能加载新增记录字段；前端对旧后端有兼容回退（推演页用冻结题面还原策略），不影响提交，但记录页新增字段须重启后端后才完整显示。本轮没有强行中断正在供测试人员使用的公网服务。

安排测试空档，运行 `stop-public.bat` 后再运行 `start-public.bat`。注意公网临时网址可能变化，密钥和数据库保留；重新分发启动窗口显示的新网址。普通本地环境关闭旧服务后运行 `start.bat`。

以后改动选项显示、排序、提交、会话恢复或学生记录时，必须同时执行：

```powershell
# 项目根目录；测试使用内存数据库和单独的临时目录，不动真实记录
$env:PYTHONUTF8='1'
$env:DATABASE_URL='sqlite:///:memory:'
.\.venv\Scripts\python.exe -m pytest backend/tests ai_component/tests -q -p no:cacheprovider --basetemp=.pytest-choice-regression
cd frontend
npm.cmd test
npm.cmd run build
```

以上环境变量只用于测试 PowerShell，不要在同一环境变量设置下启动正式应用；使用新的终端或独立双击启动脚本。

不能保证以后任意代码改动永不出现 bug；这些可重复的失败/通过测试将已知故障模式固定下来，后续发布应把它们作为门槛，而不是只检查页面是否能打开。
