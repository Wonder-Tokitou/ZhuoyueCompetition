# 发布二维码故障修复（2026-09-24）

## 根因

`teacher._qr_code_url()` 调用 `qrcode.make()`，PNG 后端延迟导入 `PIL`。
运行环境只有 `qrcode`，没有提供 `PIL` 模块的 Pillow。依赖清单漏声明，启动脚本仅检查顶层导入，未发现缺失的后端依赖。

另一处问题：原发布函数先提交 published 状态和记录成功日志，随后才生成二维码；生成失败时 HTTP 返回 500，但数据库已发布。

## 修复

- requirements 显式声明 Pillow，已安装到项目 `.venv`。
- 启动检查实际在内存中生成 PNG，安装依赖后再次验证，失败不启动服务。
- 二维码生成成功后才提交 published 状态、记录成功日志。
- 回归测试覆盖 PNG 解码、发布成功、重复发布，以及缺依赖/生成失败不写入发布状态。

## 验证与边界

- 原始 `qrcode.make()` 缺 PIL 错误已复现；安装后生成及 PNG 校验通过。
- 发布专项 4 项通过；后端全部 24 项通过（22 常规 + 2 独立进程 HTTP 日志测试）。
- HTTP 日志测试文件声明要求独立进程。全套同进程执行会产生全局日志/数据库状态干扰；本次分进程验证。
- 所有接口测试使用隔离数据库和临时二维码目录，不触碰实际案例记录。
- pip check 通过；仍有 Starlette TestClient 的 httpx 弃用警告，与本故障无关。
- 不自动修正故障前已经提交的 published 记录，不自动重启服务。重启服务后可重试发布原案例。
- 这是防止已知故障路径的措施，不保证所有未来故障都不会发生；文件系统与数据库也并非一个原子事务。
